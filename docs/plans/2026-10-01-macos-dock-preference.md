# Optional macOS Dock presence

The user requested a persisted General setting to show or hide Mimi in the Dock while it is running. Existing installations use Accessory activation policy, so `show_in_dock` defaults to false. An absent field in old preferences must preserve that behavior. The preference is global, independent of service selection; it is non-secret and uses the existing preferences transaction and settings broadcast.

The macOS runtime uses the already locked Tauri 2.11.5 activation-policy API: Regular when enabled, Accessory when disabled. Startup reads the preference before choosing the policy. It does not write system Dock pinning preferences, alter the bundle identifier/signature or grant security permissions. The existing menu-bar Settings and Quit actions remain. A Dock reopen event while enabled restores the existing settings window through the normal Settings command; disabling leaves the old reopen behavior unchanged. Windows/Linux do not display the control and reject a Dock draft without saving other changes. Settings-only IPC validation also covers Dock changes.

The settings mutation guard serializes requests. For a changed Dock choice, apply the runtime policy before saving; queue or native policy failure prevents persistence. If preference persistence fails, request the previous policy and report failure; a failed rollback emits only a sanitized status. The initial implementation only acknowledged Tauri queue acceptance; the follow-up now returns the native policy result after its main-thread transaction. Visibility/focus presentation still requires native QA. The UI blocks duplicate clicks while saving, shows a short local error, and reuses the coordinator's optimistic rollback. Ordinary unrelated saves do not request activation changes.

Validation required: legacy default and private-directory preference reload, both toggle directions, no credential operations, global preservation through profile changes, mutation failures/rollback and settings events; actual macOS Dock/Cmd-Tab appearance, toggling back, settings/overlay focus, menu-bar Settings/Quit, restart persistence, full-screen overlay with Regular. Native checks must use an isolated UI-only configuration and a coordinated installation window; CI/browser checks cannot substitute for these. Current user application must not be rebuilt/restarted without coordination. Real providers, Keychain and Dock system settings stay outside this change.


## User-reported live-window regression, 2026-10-01

Installed source `39d26b5ec7348bef0fd61e41a75413043c737e6b`: turning off Show in Dock hid the window while the user was using it. The preference must only change Dock/Cmd-Tab presence, never stop a session, hide the existing settings/subtitle windows, or lose the currently active input focus. This is an actual user report; it has not yet been independently reproduced in an isolated native package.

The locked Tauri 2.11.5 → runtime-wry 2.11.4 → Tao 0.35.3 activation-policy path directly calls NSApplication.setActivationPolicy. Tao's separate Dock path guards window canHide but uses a deprecated Carbon transform and can ignore a hide immediately after show. Do not replace the preference with that path: quick repeated clicks must not silently persist an unapplied choice, and normal Hide semantics must not remain disabled.

The follow-up changes only runtime policy application. In one main-thread transaction, snapshot the app's hidden/active state and native windows' visibility/minimized/key/canHide state, temporarily protect all existing windows from hiding, set the activation policy, restore any formerly visible non-minimized windows if needed, and restore the original key window/first responder only if Mimi was already active. Restore each window's original canHide value afterward. A background change must not activate over another app; deliberately hidden/minimized windows must not be opened. Use activateIgnoringOtherApps only inside that prior-active guard for macOS13 compatibility; NSApplication.activate is a newer API. The native YES/NO result reaches the existing save/rollback transaction before persistence. No credentials, session control, geometry, service fields or preference defaults are changed.

Contracts: Apple's [Accessory policy](https://developer.apple.com/documentation/appkit/nsapplication/activationpolicy-swift.enum/accessory) permits programmatic/window activation without a Dock entry, [canHide](https://developer.apple.com/documentation/appkit/nswindow/canhide) controls app-hide behavior, and [unhideWithoutActivation](https://developer.apple.com/documentation/appkit/nsapplication/unhidewithoutactivation()) restores without activating. The actual effect of policy changes on this OS remains a native acceptance question; compilation and the pure restoration model do not prove it.

Lightweight regression checks cover visible settings vs non-key subtitles, background focus protection, hidden/minimized restoration exclusions, existing frontend both-direction persistence/optimistic rollback, and no session toggle. Existing private-directory Rust preference reload and save_with_policy failure tests remain in CI.
